# The port

The game in Rust (docs/ROADMAP.md, phases 4-6). The 68000 code is
translated by `tools/recomp/` into **idiomatic, structured Rust**: one
function per routine, `if`/`loop`/`match` control flow, registers as
typed locals, arguments and return values, calls as Rust calls. It is not
an emulator with the decoding done ahead of time (no register file, no
program counter, no dispatch loop), and it is checked against the original
running in Genesis Plus GX, frame by frame (RAM and screens), as the SHIFT
build is.

The translated Rust (`crates/game/src/translated/`) is generated by
`make port` and committed, as a decompilation commits its C: it is the
game's code, not its data. It reads every table, graphic and sound from
the ROM the player gives the port at run time, so the port builds without
one (CI does) and no package carries any of the game. Rerun `make port`
and commit the result after changing tools/recomp or the rewrites.

## Playing it

`cargo run --release -p megafuse -- baserom.us.bin` plays the game in a
window (`crates/platform`: winit, wgpu, cpal, as VacationDestination's):
the arrows, Z X C (A B C) and Enter (Start) are pad 1, W A S D, F G H and
Tab pad 2; F11 for full screen, F2 no sprite limit (below). The window's event loop runs the game
ahead into a queue of finished frames (pictures and their sound) and
shows them at the console's pace, a frame every 16.69 ms; when the queue
is empty it runs the next step (first the boot, 155 frames at once).
Nothing waits, so the browser build (docs/web.md) is the same code.
Headless (`--frames N`) it runs some 1100 frames a second. Over the
network: docs/NETPLAY.md (`--host ROOM`, `--join ROOM`).

## A step

The game runs as its main loop does: `Game::boot` runs the reset routine
to the main loop's head (0x9368), `Game::step` one pass of the loop, from
its wait for the vertical blank to the next: a frame, or more when the
game lags (from the state, the same on every host). tools/recomp makes
the loop's head a routine of its own (`routines.STEP`) whose jumps back
return, and gives it and the reset routine one `Regs` (the registers
carry from one pass to the next, as on the 68000). Between steps the Rust
stack is empty and the game's whole state is plain data: `Game::state`
(work RAM, the time, the interrupt mask, the registers) and `md::State`
(the VDP, the Z80 and the sound chips, the pads, the I/O ports, a DMA
under way). `Game::save` copies it (some 450 KB), `Game::restore` puts it
back; the frontend gets the frame number with each frame, so what it
feeds the game (pads) depends on the frame, not on how it got there.
`megafuse --restore-check` takes a snapshot every 37 steps, runs 25,
restores and runs them again: the same clock and RAM after each, on every
script tried.

A soft reset (`jmp func_007AAE` at 0x174B2 and 0x1A76C, from a task: the
reset routine reloads sp and jumps to the loop's head) ends the step:
the reset routine runs, leaves its registers in `Game::restarted`, and
every routine between it and the step returns at once (tools/recomp
checks after each call that may lead there), as the original drops their
frames; the next step starts from those registers.

## Rewriting

Phase 4's second half: the translation rewritten as readable Rust,
routine by routine (`crates/game/src/rewritten/`), as a port rather than
an emulation: rewritten code has no console timing (no `insn`), only the
game's logic. A rewritten routine keeps the translation's signature for
now (its generated callers use it; tools/recomp writes the generated
version to `translated/rewritten.txt`) and replaces it: tools/recomp
gives the generated one `#[cfg(feature = "exact")]`.

Two builds, then:

- the port (`cargo build --release -p megafuse`): the rewrites. It no
  longer keeps the console's time where they run, so it parts from the
  original's frame-for-frame run once timing matters (the random numbers
  take in the frame count): two look-ups rewritten, stage-1-1 is the same
  to frame 464.
- the exact build (`make exact`: `--features exact`, in
  `target/exact/`): the translation everywhere, the console's time to the
  cycle. tools/port_check.py, tools/timeline_check.py and
  tools/sound_check.py run it (or `MEGAFUSE=path`): the hardware's model,
  the sound and the translator stay held to the original.

A rewrite is checked against the original call by call:
`tools/rewrite_check.py [ADDR...]` (every rewritten routine by default)
runs the original over the pad scripts (tools/mdtrace --snaps: the
registers and work RAM where each routine is entered and where it
returns, up to `--calls` a script; a call whose frame goes without a
return, as the yield's does, never ends, and the calls below it still
do) and the port's routine from each
entry state (`megafuse --routines`): the same work RAM (but the stack,
and what an interrupt during the call changes) and the same registers
and flags the callers read. `tools/routine_check.py ADDR --script ...`
does one routine, one script. A routine that waits for the frame can't
run on its own (the check says so); one no script calls is reviewed by
reading only, and its doc comment says so.

How a rewrite is written:

- One module per part of the game (`frame.rs`, `vdp.rs`, `z80.rs`,
  ...), each routine a method `r_XXXXXX` with the signature in
  `translated/rewritten.txt` (until every caller is rewritten too; then
  its interface can become what it means), its doc comment naming the
  original (`func_XXXXXX`) and saying what it does.
- Addresses become constants named for what the code does with them
  (evidence, not guesses about the game: `QUEUE_COUNT`, `REG1`, not
  `MUSIC_VOLUME` before something shows it), the address in the
  constant, a doc comment saying how it is used. Arguments get names by
  their use too.
- No `insn`, `extra` or `skip_refresh`: no console time. A wait for the
  hardware (the Z80's bus, a DMA) polls with `self.pass(cycles)` between
  tries; the wait for the vertical blank is `self.idle()`.
- Only the flags the signature returns are computed, exactly as the
  original leaves them (X travels far: see below), and only where the
  analysis says a caller reads them.
- The interrupt mask moves as in the original (`self.set_ipl`).
- Calls go to `self.r_XXXXXX` whether the callee is rewritten or not.

The analysis keeps the signatures tight (Translation, 4): no routine
returns N, Z, V and C for nothing, and data registers go by byte, word
and high word, so a routine that sets d1's low word for a callee doesn't
take d1. X stays in about a thousand: a few instructions read the X some
routine far away left (`roxr.b #4` at 0x1E3F0 stores the X
`func_0012A0` leaves, the loop's `addq` after), so it really goes
through the task routines, and the families (routines called through
one pointer) share a signature.

## Translation

`tools/recomp/` works on tools/disasm.py's analysis, in passes:

1. **Routines** (`routines.py`): an entry and what it reaches without
   passing another entry. Entries: the functions, the traces' code
   entries, jump table entries, what pointers and `move.l #code` name, and
   then, until no instruction belongs to two routines, each shared
   instruction one of them reaches from outside the other. Falling
   through or jumping into another routine is a tail call. us: 1,858
   routines, median 9 instructions, the largest 155.
2. **The stack** (`stack.py`): sp's depth through each routine, statically.
   Where it is the same wherever paths meet and 0 at every `rts`, pushes
   and pops (`movem` saves and restores) become locals and what a caller
   pushes before a call becomes the callee's arguments (`move.l #f,-(sp);
   move.b #x,-(sp); jsr func_0003E8` creates a task running `f`). 1,842
   routines are like that; the others are the patterns below.
3. **Control flow**: each routine's graph into nested Rust blocks and
   loops (the dominator-tree method WebAssembly compilers use, which maps
   onto Rust's labeled `loop`/`break`).
4. **Registers and flags**: which registers and condition flags each
   routine reads before writing and which of what it writes its callers
   use: its arguments and return values. A flag a routine returns (`ori
   #1,ccr; rts`, then `bcs` in the caller) becomes a `bool`. Tighter
   than by the instruction: an SR saved on the stack keeps its flags in
   locals of their own (`s6_w_fx`...), so a restore only passes on the
   flags read after it, and a routine that saves SR at its entry and
   restores it at every way out leaves the flags alone, like the
   registers it saves with `movem`; `roxl`/`roxr` by a constant take X
   and C from the operand; a byte or word loaded over one just written
   drops the first write; liveness goes over every local, so what a dead
   statement reads doesn't count, and data registers and temporaries go
   by lanes (bits 0-7, 8-15, 16-31: a byte or word written, a narrowing
   cast, a constant mask) while a register given back is given back
   whole; a tail call passes on only what its callee doesn't give back. The fixpoint grows from nothing, which
   over-reaches (early on a call sets nothing, so what is live after it
   is live before), and is then solved again from what the callers read
   until it holds. `dataflow.DEAD_IN` names what a routine reads that bit
   by bit never reaches its results (the random numbers' X).

   Calls through a pointer go to families (`families.py`): the sites the
   traces saw reach the same routine share one family, and the routines
   no trace reached through a pointer join one by how the code stores
   their address (pushed for `func_001222`, written to `(2,an)`, to the
   same absolute address as a traced one, or to the slot beside one in a
   table: `func_0054AE` at 0xA9AA, between `func_0093B8`'s and
   `func_00C886`'s). A target still outside the site's family (a path no
   script plays) calls the routine all the same, with a warning, rather
   than stopping the game: its family's signature may leave out a
   register this caller reads, so the warning is a lead for a script.
5. **Emission**: Rust for each instruction on those locals; memory
   through accessors (work RAM, the ROM, the hardware), which become typed
   state as each part of the game is understood.

### Patterns that need more than a call

- **The task system.** Tasks are records with a routine called once a
  frame. `func_00053E(f)` sets the running task's next routine;
  `func_000522`, called in the middle of a routine, makes the rest of that
  routine (from its return address) the next one and returns past its
  caller to the scheduler: a yield. The translator makes each such return
  address a routine of its own and the call a `return` that sets the
  continuation.
- **Returning from the caller.** `addq.l #4,sp; rts` (`func_001BB4`,
  `func_017950`) or `movem.l (sp)+,d0; rts` (`func_00D554`) drops the
  caller's return address: the callee returns a flag and the caller
  returns when it is set. `func_010BA2` (a loop's step) does it with the
  registers its callers saved too: it pops them, they are arguments, and
  the four loops that call it end when it says so. A jump to another
  routine after dropping the return address (`0x19BB0`) is a call and
  then that return.
- **Shared epilogues.** A tail that restores registers and returns,
  jumped to with them saved (`0x5010`, `0x502E`, `0x91F0`, `0x91F4`), is
  copied into each routine that jumps to it rather than made a routine.
- **Crashes.** The exception handlers (0x200-0x25F) read the exception's
  frame and show where it happened: in the port, a panic.

- **Waiting.** Most of the game runs in the tasks, once a frame. Some code
  waits in a loop: for the hardware (the Z80's bus, the VDP's DMA: done
  at once in the port), for a raster line (the HV counter: a hook at that
  line) or for a RAM flag the vertical interrupt sets (`0x805A` in the main
  loop): there the game waits for the next frame.

- `func_00D652` returns with d0 still pushed when `func_001222` can't

## Time

The port keeps the console's time exactly, as Genesis Plus GX keeps it,
so that it runs in lockstep with the original: the same interrupts land
on the same instructions, the same frame counts go into the random
numbers, the RAM is the same frame for frame. Time is counted in master
clocks (53.69 MHz NTSC; a 68000 cycle is 7, a line 3420, a frame 262
lines starting with the vertical blank's first, 224), from power-on
(the 68000 starts at line 191, 1004 clocks in, as on a Model 1).

Each instruction starts with `self.insn(PC, BASE)`
(`crates/game/src/lib.rs`), in the console's order: the last
instruction's base time is spent; the segments of the frame that ended
have their events (the frame's start, the vertical interrupt 788 clocks
into line 224, each line's start: drawing, the horizontal interrupt's
counter) and, if one started, the interrupts are checked; the bus
refresh (2 cycles every 128) is taken if due. The instruction's accesses
then happen at that time (the VDP's FIFO and DMA, the Z80's bus, which
costs a cycle), what depends on its data is added (`extra`: a branch
taken, a shift's count, MULU's bits, DIVU's steps; a long one skips a
refresh due meanwhile), and its base time waits for the next.

The times are tools/recomp/timing.py's (the 68000's tables) and the
VDP's (`crates/md`: DMA rates by mode, line and blank; the FIFO's access
slots; fills and copies busy until done). An interrupt costs 50-59
cycles by the E clock's phase; one unmasked by a write to SR is taken
in that instruction, one enabled while pending by a VDP register write
an instruction later; a DMA that runs on past its line takes the
instruction's base time with it. All of it as Genesis Plus GX does it,
which is what the port is checked against.

`tools/timing_check.py` holds timing.py to what each instruction took
in Genesis Plus GX (`tools/mdtrace --cycles`); `tools/timeline_check.py
[SCRIPT]` runs both with `--timeline` (a hash of every instruction's PC
and clock, frame by frame) and shows the first instruction where they
part. Every pad script's frames should hash the same; where they don't,
it is a time the port has wrong or a translation that does something
else (both turn up the same way: the first instruction that differs).

## Sound

The game uploads a Z80 sound driver and leaves the music and effects to
it; the 68000 only resets the Z80, holds its bus and writes its RAM.
The driver is translated too: `tools/zrecomp.py` (with `tools/z80.py`,
a Z80 decoder) turns it into `crates/md/src/driver.rs` (`make port`
writes it with the 68000's, and it is committed the same way), one
function per routine on `Sound`, structured as tools/recomp structures
the 68000's. The routines are cut where the code is called, and where
`jp (hl)` went in the traces (`zcode.us.txt`, from mdtrace `--zcover`
in `tools/trace_all.sh`). The driver never writes its own code (checked
on the interpreter over the scripts), so its code can be translated
from the ROM's copy; it starts as uploaded (`Sound::is_driver` checks
the Z80's RAM as it leaves reset, else the interpreter runs it). A
translated instruction keeps the interpreter's time
(`Sound::zin`/`zout`: its accesses after its base time, R, the
timeline) and its arithmetic (the helpers in `z80.rs` both use), so
`tools/timeline_check.py --z` holds it to the original as it did the
interpreter. A call is a Rust call, its return address pushed to the
Z80's stack; the callee's `ret` hands back what it popped.

The Z80 runs in slices up to the 68000's time, and a slice can end at
any instruction: there the translation stops (`Flow::Elsewhere`, the
PC set) and `Sound::run_until` goes on with the interpreter,
`crates/md/src/z80.rs`, as far as the next place the translation can
take up: a routine's entry, or one of its basic blocks, each of which
is a function too (to the block's end, where the runner takes the
next). Some 90% of the Z80's instructions run translated, the rest are
the ends of blocks a slice ended in. `MEGAFUSE_Z80=interp` runs the
interpreter alone. The YM2612 (`ym2612.rs`) and the PSG (`psg.rs`) are
on the Z80's bus, and the 68000's ROM through its bank window
(`sound.rs`). They keep the console's time too ("Time"), as
Genesis Plus GX runs them: the Z80 runs up to the 68000's time where
the two meet (each segment's end, a bus request, a reset) and goes on
from it when let go; its accesses happen after an instruction's base
time (`Z80::base_cycles`, measured from the interpreter itself), one to
the 68000's bus 3 cycles late (later still during a DMA). The 68000
reaches the Z80's side only while it has the bus, 8 bits wide, a cycle
late. The YM2612 makes its samples (every 1008 clocks) as far as each
access to it, so its timers overflow and its busy flag (32 of its
cycles after a write) drops on time; at a frame's end, samples made
past it are dropped and their time taken again, as Genesis Plus GX does
(its timers keep the lead). The Z80's interrupt is held from the
vertical interrupt to the end of its line. `tools/timeline_check.py --z`
holds the Z80 to the original, instruction by instruction.

The YM2612 is the Model 1's (Genesis Plus GX's default, "mame
(ym2612)"): a 9-bit DAC, the carriers truncated to it, and the DAC's
ladder effect, which makes quiet notes louder and harsher than the
total levels say (`Ym2612::model1_dac`). An operator's output is 14
bits, sign and magnitude, so a note faded far enough is 0, not a
flicker the ladder would make a buzz of. The mix is Genesis Plus GX's:
an FM channel a quarter of full scale, a PSG channel 1/16; the output
is AC-coupled (a high-pass at some 8 Hz), as the console's is, which
takes off the ladder's DC.

Sound comes out at the YM2612's rate (53267 Hz), a frame's worth
through `Frontend::audio`; `megafuse --wav FILE` and `tools/mdtrace --wav
FILE` write it out for both. `tools/sound_check.py [SCRIPT...]` runs both
on the pad scripts and compares them half a second at a time (spectra
in 63 log-spaced bands, cosine similarity; levels in dB), each block of
the port's against the original's closest within the drift, as
port_check does for RAM. It needs uv (it brings numpy). Over the attract mode
(the first 2400 frames of every script) and into the games until they
drift from the original's (some 5000-7000 frames in: the enemies move
apart), the sound is 0.995 alike and its levels within a few percent.

## Pads

`crates/md` has what the game reads its pads through, as Genesis Plus GX
has it: 3-button pads (each keeps the TH it was last given; let go as an
input, TH reads high 172 clocks later), Sega's Team Player on port A
(its handshake: header, pad types, two nibbles a pad) and EA's 4 Way Play
(port B picks the pad port A reads, or its ID). `megafuse` plugs the one
a pad script asks for (`# teamplayer`, `# wayplay`), as tools/mdtrace
does.

## The picture

`crates/md/src/vdp.rs` draws a line at its start, as Genesis Plus GX
does, and keeps to its rules where they show: colours as its 4-bit
levels widened through RGB565; sprites from the VDP's own copy of the
sprite table (written along with VRAM), found on the line before, 16 or
20 a line, masked by a sprite at X 0, 256 or 320 sprite pixels a line;
a DMA's data a window at a time (each line's before it is drawn); the
display switched off or on mid-line (the rest of the line blanked, or
the line drawn again); a change of width taken in the vertical blank or
the first three lines at once, else from the next frame.

**No sprite limit** (F2, `--no-sprite-limit`): every sprite on a line is
drawn, the last one whole, where the console stops at 20 a line or 320
pixels. Mostly it shows in the menus (text dropped while the panels
slide in) and the title's explosion; in play where many bombs and
enemies share a line. The switch only changes the picture: the status
flags (overflow, collision) and the masking are counted as the
console's, so RAM stays the same (every script's run with it on has the
same RAM, frame by frame, as without), and peers in a network game can
each have it either way. The frontend gives it to the machine at each
frame's start, so a rollback's snapshot doesn't carry it.

## Checking it

`tools/port_check.py [SCRIPT...]` runs the port (`target/release/megafuse`)
and the original in Genesis Plus GX on the pad scripts with `--hashes`
(each frame's CRC-32 of work RAM, the stack aside, and of the picture)
and reports the first frame that differs, dumped: the RAM bytes, the
pixels. Every pad script has the same RAM and the same picture, frame
for frame, for its whole length, and the same 68000 and Z80 timelines
(`tools/timeline_check.py`). `--vram PREFIX` on both dumps VRAM, VSRAM,
the sprite table's copy and the registers; `tools/sound_check.py`
compares the sound.
